*** Design decisions (current best answers, to confirm in Lyon)
- Object = a *defining form* (unambiguous, ideally position-space) + materialisations
  cached per basis key. A "matrix" is a view, not the thing itself.
- Expectation values stay outside the class: expose symmetry-sector blocks, and let a
  separate generic evaluator compute $\mathrm{Tr}(\rho\,Q)$ from any object exposing
  such blocks. Keeps the class testable in isolation.
- Quasiparticle and position representations: derived on demand and cached under the
  basis key, never stored as a second authoritative copy.
- The basis key ("which basis?") must carry: truncation, which of P/T/Rz/STy are
  imposed, phase / gauge convention, producing-code version. All four or benchmarks rot.
- Generalise (anti-)Hermiticity to conjugation classes: encode relations like
  $Q_{\ell,-m}=(-1)^m Q_{\ell m}^{*}$ and the T- or STy-induced reality conditions;
  the Hermitian / anti-Hermitian boolean only covers the simplest case.
- Each operator declares which symmetries it may break. v1 may exploit the block
  structure only for invariant operators, but the machinery must not choke on
  sector-mixing ones (FAM perturbations, cranking fields).
- Reuse MOCCa's runtime bookkeeping instead of reinventing it: the symmetry blocks
  HFBlocks(8) (p/n x hermitian-like x antihermitian-like, wavefunctions.f90:147) and
  the per-spwf reflection labels sx/sy/sz(4,nwt). Quantum-number logic currently
  lives in two layers: those runtime labels + Hephaestos compile-time expansion
  ($TR/$NTR/...). Decide which layer the class takes over.
- MPI is a first-class design constraint: spwfs are rank-local (rank_map/spwf_map/
  spwf_inverse), MEs are computed on designated ranks and merged with full-size
  ALLREDUCEs -- flagged improvable in the momentsofinertia.f90 TODOs. Storage must
  be rank-local per symmetry block.

*** Conjugation-class machinery (proposal, elaborated)
- Observation :: the ~40 routine family + the sign conventions of the caller
  (momentsofinertia.f90:830+, incl. the "attention to the sign(s)!" comment)
  hard-code, per (component, symmetry case), (a) which MEs vanish, (b) which are
  pure Re or pure Im, (c) the fill-by-transpose sign. In my proposal these become
  *derived* from metadata.
- Metadata :: each operator declares its characters: Hermitian or anti-Hermitian,
  eigencharacter under the exact-symmetry generators (P, T, R_z, STy as applicable).
  Tensor operators get characters for free: $Q_{\ell m}$: parity $(-1)^{\ell}$,
  $R_z$ character $(-1)^m$, T-even; $J_{\mu}$ analogous. FAM perturbations: declared.
  Symmetry-breaking operators have no characters: the machinery degrades (no
  selection rules) instead of breaking.
- Derivation :: characters + per-spwf labels sx/sy/sz -> coupling table: live block
  pairs, representative (i,j) pairs, phase multipliers along orbits, and the reality
  class (Re vs Im) of the stored number. Same trick moments.f90 already uses for
  *densities* ($Y_{l,-m}=(-1)^m Y_{lm}^{*}$, m >= 0, Re/Im split) extended to matrices.
- Layers :: character metadata -> coupling table (derived per symmetry scenario) ->
  thin mesh-integration kernels, with the O-T variants reduced to applying the
  existing TimeReverse() to the wavefunction arguments -> triangle storage per live
  block pair -> materialisation to complex matrices / basis transforms.
- Priority ramp revisited :: P -> T -> Rz -> STy is the same table gaining one
  generator row at a time; each step is one new regression class. Compile-time
  fork: derive the tables at runtime, or have Hephaestos specialize them per
  scenario -- the latter keeps MOCCa's existing strategy.
- Risks :: the phase multipliers are where sign bugs live (hence golden outputs
  first); scenario coverage must first reproduce $TR/$NTR behavior exactly; tables
  live over global indices (MPI); keep inner mesh loops specialized -- generic
  bookkeeping, not generic kernels.

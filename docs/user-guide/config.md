# The configuration file

A configuration file specifies many - though not exactly *all* - of the compiletime options of MOCCa. 

## The functional file 

The variable `FUNC_FILE` selects the analytical form of the Skyrme functional. It must correspond to a valid functional file in the `functionals/` folder.

## Self-consistent symmetries

The variable `SYMSTRING` encodes the self-consistent symmetries that will be enforced / numerically exploited in the calculation. It is a comma-separated string of up to four operators out of the following: 

- ``Rz`` : signature around the z-axis
- ``T`` : time-reversal 
- ``P`` : parity
- ``STy``: y-time-simplex

For example, the following string will result in a MOCCa executable that operates in maximally symmetric mode. 
```python 
SYMSTRING = 'Rz,T,P,STy'
```

The variable `REDUCE` tells the code *how* to leverage the spatial symmetries. For each Cartesian direction, 0 indicates that the full axis is represented in memory while 1 indicates that calculations are limited to the positive semi-axis. 

For example:
```python
REDUCE    = [1,1,0]
```
indicates that one-fourth of a Cartesian cube will be simulated: the full z-axis, but only half of both the x- and y-axis. 

Note that `REDUCE` does not nearly realize all of its potential. The current implementation only offers the illusion of a choice: if parity is conserved/broken, you should specify `[1,1,1]` / `[1,1,0]`.

## Symmetries read from file

Any MOCCa executable is capable of reading wavefunction files generated by either (i) another MOCCa executable operating with the same set of enforced selfconsistent symmetries *or* (ii) a MOCCa executable with *exactly one more* self-consistent symmetry.  The latter is controlled by the variables `INSYM` and `INREDUCE`: these follow the same conventions as `SYMSTRING` and `REDUCE` but apply to the more symmetric type of calculation that you want to use as warmstart.  

## Axis orientation for multipole moments

The definition of the multipole operators $Q_{\ell m}$ involves spherical harmonics $Y_{\ell m}$, which in turn depend on the definition of a spherical coordinate system $(r,\theta,\phi)$. Hence, the $Q_{\ell m}$ depends on the specification of the angles $\theta, \phi$ w.r.t. to the Cartesian axes $x,y,z$. 

This can be controlled through the variables `QUANT_AXIS` and `SECOND_AXIS`. The first specifies the axis to which $\theta$ measures the inclination, i.e. the Cartesian coordinate that is equal to $r\cos \theta$
; in most textbooks this is `Z`. `SECOND_AXIS` then specifies the axis to which $\phi$ measures the inclination, i.es. the Cartesian coordinate that is equal to $r \sin \theta \cos \phi$. `SECOND_AXIS = 1` selects this axis as the first one in the lexicographical ordering of the two remaining axes, which is a right-handed ordering. `SECOND_AXIS = 2` selects the other alternative.

Hence, the options are
```python
# Z - axis for \theta, X for \phi
# this is the "textbook" definition of the multipole moments
QUANT_AXIS = 'Z'
SECOND_AXIS= 1  # the lexicographical ordering is ['x', 'y']

# Z - axis for \theta, Y for \phi
QUANT_AXIS = 'Z'
SECOND_AXIS= 2

# X - axis for \theta, Y for \phi
QUANT_AXIS = 'X'
SECOND_AXIS= 1

# X - axis for \theta, Z for \phi
QUANT_AXIS = 'X'
SECOND_AXIS= 2

# Y - axis for \theta, X for \phi
QUANT_AXIS = 'Y'
SECOND_AXIS= 1

# Y - axis for \theta, Z for \phi
QUANT_AXIS = 'Y'
SECOND_AXIS= 2

```

It might naively seem that all of these options are equivalent in terms of physics, as this resembles a change of axes. This would be true if the exchange of axes would be *complete* but it is not: we do not change the axes referenced by the self-consistent symmetries - e.g. `Rz`. Only in a (hypothetical) fully symmetry-unrestricted calculation are all of these options interchangeable. 

## Decoupling of particle-hole and particle-particle fields

`PH_PP_DECOUPL` is a highly advanced option regarding the treatment of functional forms; perhaps it should be moved to the .param specification of individual parameterisations in the future. 

This parameter specifies whether the code accounts for any density-dependence of the pairing terms of the functional in the construction of the particle-hole meanfields. For example, the typical "ULB pairing terms" look like 

$$
 E_{\rm pair} \sim \frac{1}{4}\sum_{\rm q = p/n} V_{q} \Big[ 1 - \alpha \rho_0(\mathbf{r})\Big] \tilde{\rho}_q(\mathbf{r}) \tilde{\rho}_q
 (\mathbf{r}) \, 
$$

with parameters $V_p, V_n$ and $\alpha$ and the usual notation for the pairing densities $\tilde{\rho}_q(\mathbf{r})$. The variation of these terms w.r.t. to the isoscalar density $\rho_0$ is evidently not zero and would contribute to the mean-field potentials, but this contribution is nevertheless set to zero for most older Skyrme models.

If `PP_PP_DECOUPL = True`, this contribution and those that are conceptually similar are ignored in the calculation. `PP_PH_DECOUPL = False` enables a completely consistent calculation.
